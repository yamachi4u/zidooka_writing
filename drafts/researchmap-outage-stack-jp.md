researchmapが、最近かなり不安定です。ページが開かなかったり、「アクセスが集中しています」のような状態になったり、一部機能だけ止まったりすることがあります。

単に「アクセスが多いから」で済ませると雑すぎます。公開情報を追うと、現在のresearchmapには、かなり具体的な技術的事情が見えてきます。

:::conclusion
2026年8月時点で最も筋が通る説明は、**NetCommons3を大幅拡張した比較的レガシーなLAMP系アプリケーションに大量の動的アクセスが集中し、アプリケーション／DB側がボトルネックになっている**というものです。

Cloudflareのような大規模CDNを前段に置いて静的配信・キャッシュ・Bot制御を広く吸収している形跡は薄く、JST自身も2025年末以降のアクセス急増によるシステム負荷を公式に認めています。
:::

## まず、JST自身が「アクセス急増で障害」と認めている

2026年6月2日、JSTは「昨年末頃から、researchmapへのアクセスが急増」し、その結果として「ウェブページが見られない」「一部の機能が停止する」といった障害が断続的に発生していると公表しました。

さらに、アクセス急増の一因として外部検索エンジンのクローリングを挙げ、2026年1月から業績詳細ページやブログ等への検索エンジンの情報収集を制限しています。

つまり、少なくとも運営側の認識では、障害の主因は**外部からの大量アクセス → システム負荷上昇**です。

ただし、ここで疑問が残ります。

現代的な大規模Webサービスなら、検索Botや未ログイン閲覧のかなりの部分は、CDN、キャッシュ、WAF、レート制限などで前段処理できます。なぜresearchmapでは、そのアクセスがアプリケーション全体の停止につながるのでしょうか。

## researchmap v2の土台はNetCommons3

これは推測ではありません。

researchmap v2は、NetCommons3をベースに構築されています。NetCommons公式サイトには、researchmap v1からv2への移行とNetCommons2から3への移行ツールの関係が記録されています。

さらに2025年のJST調達資料は、現行researchmapがNetCommons3の標準機能と拡張改修機能の双方を利用していると明記しています。

そして、その資料にはかなり重要な記述があります。

現行システムについて「NetCommons3をどのように利用して各種機能を実現しているかを示す設計書が存在しない」ため、脆弱性や不具合が発生した際の原因特定・改善策調査に「多大な時間を要し、安定運用上の大きな懸念」となっている、というのです。

このためJSTは、2025年度に現行ソースとDB構造を対象としたリバースエンジニアリング、CRUD図整備、NetCommons3利用状況のドキュメント化を発注しています。

:::note
これはかなり重い情報です。単に「古いCMSを使っている」という話ではなく、**巨大なカスタマイズシステムに対して、保守に必要な設計情報が不足しているため、後からリバースエンジニアリングしている**ということです。
:::

## バックエンドはLAMP系と考えてよい

2026年7月にJSTが掲載したresearchmapシステム担当者の求人では、必須要件として以下が挙げられています。

- Linux
- Apache
- MySQL
- Apacheアクセスログの解析
- SQLによるデータ抽出・集計
- DNSの理解
- シェルスクリプト

NetCommons3自体もPHP系CMSです。

したがって、現行researchmapの中心部分は、概ね次のような構成と推定できます。

```text
Browser / Bot
     ↓
Internet
     ↓
[ロードバランサ / リバースプロキシ？]
     ↓
Apache
     ↓
PHP / NetCommons3 + researchmap独自機能
     ↓
MySQL
     ↓
研究者・業績データ
```

ただし、ロードバランサや内部リバースプロキシの具体的製品、台数、DBレプリケーション構成などは公開情報から確認できません。

## Cloudflareは使っているのか

少なくとも、一般的な「Cloudflareをオレンジ雲にして、Cloudflareのエッジをresearchmapの公開フロントにする」形には見えません。

公開DNS情報では、`researchmap.jp` のAレコードは `160.74.72.2` を指しています。このIP帯はAS2513、つまりJapan Science and Technology Agency自身のネットワークです。

ネームサーバもCloudflareではなく `ns1.do-reg.jp` / `ns2.do-reg.jp` です。

また、証明書はJST組織名入りのDigiCert証明書です。

したがって、観測できる範囲では、典型的なCloudflare Proxy構成ではなく、かなり直接的にJST側ネットワークへ到達しているように見えます。

もちろん、**JSTネットワーク内部に独自のL7ロードバランサやリバースプロキシが存在する可能性は十分あります**。公開Aレコードが1個だからWebサーバも1台、という意味ではありません。`160.74.72.2` がVIPで、その背後に複数Apacheがある構成も普通にありえます。

重要なのは、Cloudflareのような外部CDN・Bot Management・巨大なエッジキャッシュ層が前面に見えてこないことです。

## なぜ検索Botで落ちるのか

ここからは推定です。

researchmapのページは、研究者トップだけでなく、論文、MISC、書籍、講演、ブログ、コミュニティなど非常に多くのURLを持っています。研究者数も多く、1人あたり多数の業績詳細URLがあります。

検索Botがこれを深くクロールすると、単なるHTMLファイル取得ではなく、リクエストごとにApache/PHP/NetCommons3が起動し、MySQLへ問い合わせ、アクセス権やプラグイン、各種関連データを処理してHTMLを組み立てる可能性があります。

もしページキャッシュが弱い、あるいはログイン状態・権限・ウィジェット構成等のためキャッシュ効率が悪いと、Botの大量巡回がそのままDB負荷・PHPワーカー枯渇・Apache接続枯渇につながります。

典型的には、次のような連鎖です。

```text
Google/Bing/AI crawler等が大量URLを巡回
        ↓
Apacheへの同時接続増加
        ↓
PHP処理数増加
        ↓
MySQL query増加
        ↓
遅いquery / lock / connection増加
        ↓
PHP workerが返ってこない
        ↓
Web workerが詰まる
        ↓
通常ユーザーも待たされる
        ↓
「アクセス集中」・タイムアウト・機能停止
```

Cloudflare等が強く前段にいれば、公開プロフィールや業績詳細のような「匿名ユーザー向けGET」はEdge Cacheでかなり吸収できます。Botごとのレート制限やChallengeも容易です。

しかし、そうした層が弱い場合、世界中のBotが直接LAMPアプリケーションを叩くことになります。

## 2026年1月から「検索結果に出なくする」で逃がしている

JSTが取った暫定策も示唆的です。

負荷を抑えるため、2026年1月から外部検索エンジンによる業績詳細やブログの情報収集範囲を制限しました。

これはアプリケーション内部を高速化したというより、**入口のトラフィックそのものを減らして耐えている**対策です。

もし十分なキャッシュ／CDN／Bot制御レイヤーだけで解決できているなら、研究成果がGoogle等に出なくなるという大きな副作用を受け入れる必要は本来ありません。

その意味で、JST自身の対策は「現行基盤ではクロール負荷を安全に受け切れない」ことを間接的に示しています。

## 2029年に全面リニューアル予定

2025年10月、JSTは現行researchmapが利用する基盤ソフトウェアのサポート終了に伴い、2029年に次期researchmapへリニューアルする計画を公表しました。

改善項目として明示されているのが、

- システム保守性の向上
- セキュリティの向上
- パフォーマンスの向上

です。

しかも、次期システムでは業績検索、フォロー機能、多数のNetCommons的ウィジェット、ブログ、掲示板、汎用DBなどを廃止・縮小する方針です。

これは合理的です。researchmapに本当に必要なのは「研究者情報と業績の登録・公開・API連携」であって、CMSとしての大量の周辺機能まで背負う必要は薄いからです。

機能を削るほど、データモデルも画面生成も権限管理もキャッシュ戦略も単純化できます。

## 追記：2026年には、もう「更改の稼働環境」を調達している

その後の調達情報を追うと、話はもう一段進んでいました。JSTは2026年5月7日付で、**「researchmapシステムの更改に係る稼働環境構築業務」**を一般競争入札に付しています。履行期限は2027年3月31日です。

つまり、2029年リリースは単なる構想段階ではなく、少なくとも2026年度には次期システムを動かす環境の構築フェーズへ入っています。

一方、公開されているJSTの案内は「現在使用する基盤ソフトウェアのサポート終了に伴うリニューアル」と表現しており、次期researchmapがNetCommons4なのか、別フレームワークなのか、クラウドネイティブへ移行するのか、といった具体的なアプリケーションスタックまでは現時点で確認できません。

:::note
したがって、「2029年にNetCommons3を捨てる」はかなり自然な推測ですが、**次期researchmapがNetCommons系そのものを完全に捨てると断定できる公開資料は、今回確認した範囲では見つかりませんでした**。
:::

## むしろ重要なのは「何のフレームワークか」ではない

10年以上使う公共系システムを考えると、Next.js、Laravel、Rails、Spring Bootのどれが正解か、という問いだけでは不十分です。

JavaScript系の最新フレームワークは開発速度では魅力的ですが、10年単位ではフレームワークや周辺ライブラリの変化がかなり速い。一方、JavaやPHPなど比較的保守的な企業向けスタックは長期保守しやすい反面、古い設計を抱えたまま延命すると今回のような技術的負債にもなります。

researchmapで本当に効くのは、特定の流行スタックよりも、次のような設計でしょう。

- 研究者・業績データをCMSの内部構造から分離する
- 公開プロフィールは極力キャッシュ可能にする
- APIを安定した契約として独立させる
- Web/Appサーバをステートレス化し、水平スケール可能にする
- CDN/WAF/Bot Managementを前段に置く
- DBの読み取り負荷を分散できる構成にする
- ソースだけでなくデータモデル、API、運用手順を継続的に文書化する
- フレームワーク更新を「全面更改」ではなく通常保守で回せる境界を作る

特に最後が重要です。今回の問題は「PHPだから」「NetCommonsだから」だけではなく、**基盤ソフトウェアの寿命とresearchmap本体の寿命が強く結合してしまったこと**にもあります。

理想は、UIやフレームワークを交換しても、研究者・業績データ、認証、API、検索などの中核を段階的に移行できる構成です。

:::conclusion
長期間運用するresearchmapで重要なのは、「2026年に一番モダンなスタック」を選ぶことではなく、**2036年にそのスタックを捨てる必要が出ても、システム全体をリバースエンジニアリングし直さずに交換できること**です。

2029年更改で見るべきなのは、Next.jsかPHPかという表面的な選択以上に、モジュール境界、API、データモデル、キャッシュ、観測性、ドキュメント、アップグレード戦略です。
:::

## ではCloudflareを入れれば全部解決するのか

そう単純ではありません。

CloudflareやFastly、CloudFrontなどを前段に置けば、匿名GETのキャッシュ、WAF、DDoS耐性、Botレート制御はかなり改善できます。

ただし、PHP処理そのものが重い、N+1 queryが多い、MySQLのindex設計が悪い、セッション依存でキャッシュできない、ログイン後画面が重い、バッチ処理がDBを圧迫する、独自プラグイン間の依存が複雑、といった問題はCDNだけでは解決しません。

そのため理想的には、CDN/WAF/Bot Management、L7 Load Balancer、Stateless Web/App servers、Cache/Session、適切にチューニングされたRDBMSという複数層で受ける必要があります。

## 現時点の推定まとめ

| 項目 | 推定 | 確度 |
| --- | --- | --- |
| 基盤CMS | NetCommons3 | 高：JST調達資料等で確認 |
| OS | Linux | 高：JST求人で明示 |
| Webサーバ | Apache | 高：JST求人で明示 |
| DB | MySQL | 高：JST求人で明示 |
| アプリ | PHP + NetCommons3 + 大規模独自改修 | 高〜中 |
| Cloudflare Proxy/CDN | 前段利用の形跡は薄い | 中 |
| 内部ロードバランサ | 存在する可能性あり | 不明 |
| 主障害要因 | 大量アクセスによるApp/DB負荷 | 高：JSTがアクセス急増との因果を公表 |
| 次期システム | 2026年度に稼働環境構築の調達開始 | 高 |
| 次期アプリスタック | 未確認 | 不明 |

:::conclusion
researchmapが落ちやすい理由を「国のサイトだから古い」で片付けるのは雑ですが、公開資料を並べると、かなり構造的な問題が見えます。

**NetCommons3を核に長年拡張した巨大システム、LAMP系の動的処理、大量クロール、設計資料不足、そして2029年まで続く旧基盤。**

一方で、2026年には次期システムの稼働環境構築がすでに調達に出ています。次に注目すべきなのは「NetCommonsを捨てたか」だけではなく、次の10年で同じ巨大モノリスを作らない構造になっているかです。
:::
