AIに記事を書かせると、文法的には間違っていないのに、どこか均一で、説明のための説明が続く文章になりがちです。そんな問題に正面から取り組んでいるのが、cojiさんの `natural-japanese` です。

これは、仕事の日本語やブログ、エッセイを読みやすく書くためのAgent Skillです。単なる「AIっぽい表現リスト」ではありません。書く前の設計、生成時の文体制約、書いた後の機械的な検査をひとつの流れに組み込んでいます。

## 何が面白いのか

いちばん重要なのは、「検出は機械、判断は人間またはAI」と役割を分けていることです。

AIは、自分が書いた文章のAIらしさをうまく認識できません。そこで `lint.py` が、禁止語や紋切り型の表現、文のリズム、段落構造、英語の直訳調を検出します。ただし、検出された表現を必ず消すわけではありません。文脈上必要なら残してもよく、何をどう直すかは書き手が判断します。

この分離はかなり大切です。「この言葉を使ったら即アウト」というルールにすると、文章は逆に不自然になります。機械は疑わしい場所を示し、書き手はその文章の目的と読者を考えて修正する。校正支援として筋のよい設計です。

## 12箇条の文体憲法

`natural-japanese` には、生成時に意識する12箇条の文体憲法があります。たとえば、結論から書く、見出しをメッセージにする、専門用語を文中で説明する、同じ構文を繰り返さない、といった原則です。

ここで面白いのは、完成後に「AIっぽさ」を消すだけではなく、最初から発生しにくい条件を作っている点です。段落の形や見出しが毎回同じになる問題は、単語を置き換えるだけでは直りません。読者、主メッセージ、見出しの骨格を先に決める必要があります。

## 検査できるものと、検査しないもの

このスキルは、何でも数値化しようとはしていません。禁止語や定型句は機械的に検出します。一方、語順、読点、一文の重さ、主語と述語の距離のような読みやすさは、単純な閾値だけでは判断しにくい。そこで、読解負荷の高そうな箇所を機械が示し、最終判断は人間またはAIに残しています。

この控えめさがよいところです。文章の読みやすさを、ひとつのスコアに押し込めていません。

## zidookaの執筆にどう取り込むか

zidookaでは、記事を日本語版と英語版で作り、GitHub Actions経由で公開しています。ここに取り込むなら、次の三層が現実的です。

### 1. 記事を書く前の設計をテンプレート化する

記事の下書きに、次のメタ情報を持たせます。

- 読者は誰か
- この記事で最初に伝えることは何か
- 読者が読み終えたあとにできることは何か
- 見出しごとのメッセージは何か
- 日本語版と英語版で変えてよい部分はどこか

これだけでも、いきなり本文を書き始めるより、記事の論旨が安定します。

### 2. 投稿前に自然さの検査を入れる

`natural-japanese` の `lint.py`、`outline.py`、`terms.py` を、投稿前の確認手順に組み込みます。最初からCIで落とすのではなく、まずは警告として結果を出すのがよさそうです。

記事の公開を止めるゲートにすると、必要な定型表現まで削る危険があります。最初は「検出結果を見て、直すか、残す理由を判断する」運用にします。

### 3. 日本語版と英語版を同じ型にしすぎない

日英記事では、タイトル、導入、結論を機械的に一対一対応させると、英語版が日本語の直訳になりやすい。共通の事実と主張は保ちつつ、英語版では英語の読者に必要な前提を補い、日本語版では日本語の読者に自然な導入を使う方がよいでしょう。

## まず使うなら

リポジトリのREADMEにある手順では、次のように導入できます。

```bash
npx skills add coji/natural-japanese
```

検査スクリプトだけを試す場合は、リポジトリ内で次のように実行します。

```bash
uv run skills/natural-japanese/scripts/lint.py path/to/draft.md
uv run skills/natural-japanese/scripts/outline.py path/to/draft.md
uv run skills/natural-japanese/scripts/terms.py path/to/draft.md
```

`lint.py` は文章を自動的に書き換えるものではありません。疑わしい箇所を挙げ、どう直すかは書き手に委ねます。ここを誤解しないことが重要です。

## 結論

`natural-japanese` は、AIに「もっと自然に書いて」と頼むためのプロンプト集ではありません。文章を設計し、制約し、検査し、必要なら修正するための執筆工程です。

zidookaに取り込むなら、まずは記事ごとの設計メタデータと、投稿前の警告型lintから始めるのがよさそうです。将来的には、検出結果をGitHub Actionsのアーティファクトとして残し、修正前後の差分を確認できるようにする。そうすれば、記事の量を増やしながら、文章の均一化やAIっぽさを抑えられます。
