GitHubで[BlockのBuzz](https://github.com/block/buzz)というOSSを見つけました。説明を読むと、かなり面白いです。

:::conclusion
Buzzの面白さは、AIエージェントを「チャットボット」として外付けするのではなく、人間と同じようにチャンネルへ参加するメンバーとして扱い、会話・Git・CI・ワークフロー・監査ログを一つのイベントログにまとめようとしている点です。
:::

## Buzzは何か

Buzzは、セルフホストできるチーム向けワークスペースです。デスクトップアプリはTauri＋React、サーバー側のリレーはRustで構成されています。

土台になっているのはNostrのイベントモデルです。メッセージ、リアクション、ワークフローの実行、レビュー承認、Gitイベントなどを、署名されたイベントとして同じログに記録します。

見た目はチームチャットに近いのですが、発想としては「会話を中心にしたプロジェクト記録」に近いです。

## 何が普通のAIツールと違うのか

一般的なAI開発ツールでは、AIはチャット欄やIDEのサイドバーにいます。人間が質問し、AIが回答し、必要に応じて別のツールを操作します。

Buzzでは、エージェントに固有の鍵ペアとアイデンティティを持たせ、チャンネルのメンバーとして参加させます。人間とエージェントは、同じ部屋で会話し、パッチを出し、CI結果を確認し、レビューを受けます。

:::note
AIに強い権限を一括で渡すのではなく、エージェント自身のアイデンティティ、チャンネル所属、署名済みイベント、監査ログを組み合わせて扱う設計です。
:::

この考え方は、AIを「便利な秘書」として使うより、複数の作業主体がいるチームの一員として使う場合に向いていそうです。

## GitHubの代替というより、GitHubの前後をつなぐもの

Buzzが特に面白いのは、Git機能をチャットから切り離していないことです。

ある機能ブランチを開いたら、そのブランチに対応するチャンネルを作り、そこへパッチ、CI、レビュー、承認、マージ判断を集める、という構想があります。

これは「コードはGitHub、相談はSlack、CIは別画面、判断の根拠は議事録」という分散を減らす発想です。

:::example
バグの調査で、エージェントが過去のチャンネルから似た事例を探し、関連スレッド、原因、修正、担当者を根拠付きで投稿する。質問と回答と証拠が同じ場所に残るため、後から経緯をたどれます。
:::

## Nostrを使う意味

Nostrを採用することで、メッセージや操作主体を暗号署名付きイベントとして扱えます。Buzzでは、これを単なる分散SNSのためではなく、チーム内の「誰が何をしたか」を記録する仕組みに使っています。

署名されているから自動的に正しいわけではありません。ただ、AIエージェントが増えるほど、生成物の内容だけでなく、どのアイデンティティが、どの文脈で、どの操作をしたのかが重要になります。

Buzzはそこを、権限フラグだけでなく、アイデンティティとイベントログの問題として捉えています。

## 現時点で気になるところ

かなり野心的なプロジェクトなので、まだ完成品というよりプロトタイプとして見た方がよさそうです。

README上では、リレー、チャンネル、スレッド、DM、キャンバス、メディア、検索、監査ログ、デスクトップアプリ、buzz-cli、YAMLワークフロー、Gitイベントなどが「動作するもの」とされています。一方、モバイルクライアントやワークフローの承認ゲートなどは開発中です。

また、Nostrの鍵管理、セルフホストの運用、検索インデックス、ファイル保存、マルチコミュニティの境界など、実際にチームで使うには確認したい点も多いです。

:::warning
READMEに書かれたビジョンと、現時点で安定して使える機能は分けて見た方がよいです。組織の中核コミュニケーションを移す前に、バックアップ、鍵の紛失時対応、アクセス制御、検索の完全性、監査ログの保全を確認する必要があります。
:::

## どう動かすのがよさそうか

Buzzは、いきなり本番のチーム基盤にするより、段階的に試すのがよさそうです。

:::step
まずPCにBuzzをクローンし、DockerとHermitを用意して、just setup、just build、just devを実行します。リレーは基本的に ws://localhost:3000 で起動します。
:::

最初は自分一人で、チャンネル作成、スレッド、検索、buzz-cli、エージェント連携、Gitイベントを確認します。そのうえで、実際の小さな開発作業を一つだけ載せてみるのがよさそうです。

次の段階では、PC上のリレーを外部から使えるようにします。Cloudflare PagesにBuzz本体を置くのではなく、PC上で動いているリレーをCloudflare Tunnel経由で公開する形です。

```text
Buzz desktop / スマホ
          ↓
Cloudflare Tunnel
          ↓
自宅PCのBuzz relay
```

Cloudflare Tunnelなら、ルーターのポートを直接開けずに、自宅PCで動くサービスを外部へ接続できます。ただし、PCをスリープ・終了するとBuzzも止まります。無料で試すには便利ですが、常用サーバーとしては不安定です。

:::warning
Cloudflare PagesだけではBuzzのリレーは動きません。BuzzはRustのリレーに加えて、Postgres、Redis、S3／MinIOなどを使う構成なので、静的サイトのホスティングとは別物です。
:::

常用する段階になったら、Railwayのワンクリックデプロイ、またはVPSへリレーを移すのが現実的です。Cloudflareはその前段のDNS、HTTPS、Tunnel、アクセス制御に使う、という役割分担になります。

:::conclusion
最初は「PC内で試す → Cloudflare Tunnelで外から触る → 使い続けるならRailway／VPSへ移す」が一番無理のない進め方です。まず確認すべきなのは、AIエージェントをチャンネルのメンバーとして置いたときに、本当に作業履歴が見やすくなるかどうかです。
:::

## これはSlackの代替なのか

単純なSlackクローンではありません。Slackのような会話の場に、Gitホスティング、CI、エージェント実行、ワークフロー、プロジェクト記憶を同じイベントモデルで接続しようとしています。

Buzzの本当の競争相手はSlack単体ではなく、チャット、GitHub、CIダッシュボード、自動化ツール、AIエージェントの実行環境、社内検索、監査ログをつなぐ大量の連携部分なのだと思います。

:::conclusion
Buzzは、AIを追加したチャットアプリというより、「人間とAIが共同で作業した履歴そのもの」をプロジェクトの基盤にしようとするOSSです。まだ発展途上ですが、エージェントが増える時代のチームウェアを考えるうえで、かなり筋のよい問いを投げています。
:::

現状は、まずローカルで試して、buzz-cliやエージェント連携、Gitイベント、セルフホスト時の運用感を確認してみたいところです。
