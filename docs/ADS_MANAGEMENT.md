## 2. 問題点（組み直しの前に直すべき構造問題）

### P1. 広告コードが3ファイルに分散し、単一の台帳がない
どこに何の広告があるかを知る方法が「grepする」しかない。配置変更のたびに
複数ファイルを触ることになり、消し忘れ・二重貼りの温床。

### P2. AdSenseのA2とA3が同じスロットID
タイトル直上と本文直後が同じユニット `2410921395` なので、
**AdSenseレポート上でどちらの位置が稼いでいるか判別できない**。
組み直しの効果測定が原理的に不可能な状態。組み直し前に必ず分離する。

### P3. A8の実装品質が2系統で不一致（コンプライアンス問題を含む）
- サイドバー(B2)は `zidooka_render_banner` 経由: **Sponsoredラベルあり**、
  PostHog `banner_exposure`/`banner_click` あり、lazy loading あり
- 本文内(B1)は生HTML直書き: **広告ラベルなし**、計測なし、`rel="nofollow"` のみで
  `sponsored` なし、同一バナーを2回挿入
- 景表法ステマ規制（2023年10月〜）的に、本文内バナーの**ラベル無しは要修正**。
  これは組み直しを待たずに直すべき唯一の項目。

### P4. A8案件リンクの生存確認プロセスがない
a8matはプログラム終了で死ぬ（リンク切れ画像になり収益ゼロ）。
Xserverは2025-12発行、FPカフェは2026-07発行のコード。誰も死活を見ていない。

### P5. A8の成果データが管理サイクルに入っていない
AdSenseは `npm run adsense` でAPIから取れて `npm run improve` にも組み込まれているが、
A8はA8管理画面を見に行かない限り成果が分からない。
「AdSenseとA8のどちらを優先すべき配置か」を判断する材料が揃わない。

### P6. 出し分けルールが暗黙的
- `affiliate` タグ → AdSense全排除（誤クリック・競合回避としては合理的だが文書化されていない）
- `xserver` 系タグ → Xserverバナー、それ以外 → FPカフェ
- FPカフェが「その他すべての記事」のデフォルトなのは案件マッチ度が低い
  （読者の大半はAIツール・エラー解決目的の技術系）

## 3. 管理設計の提案

### 3.1 単一台帳: プレースメント・レジストリ

テーマに `inc/ads.php` を新設し、広告に関するコードを全部そこへ移す。
中心はプレースメント定義の連想配列（＝台帳）:

```php
// 概念図。キーは「位置」であって「案件」ではない
zidooka_ads_registry() => [
  'post_title_top'    => ['provider' => 'adsense', 'slot' => '<新スロット>', 'pages' => ['post']],
  'post_below_content'=> ['provider' => 'adsense', 'slot' => '2410921395',  'pages' => ['post']],
  'post_in_content'   => ['provider' => 'a8', 'offer' => 'by_tag', 'positions' => [3, 5]],
  'sidebar'           => ['provider' => 'a8', 'offer' => 'by_tag'],
  'front_page'        => ['provider' => 'adsense', 'slot' => '1657762831', 'pages' => ['front']],
];

// A8案件は別テーブルで管理（追加・差し替え・停止をここだけで完結させる）
zidooka_a8_offers() => [
  'xserver' => ['click' => '...', 'img' => '...', 'pixel' => '...', 'w' => 336, 'h' => 280,
                'tags' => ['xserver','server','hosting','wordpress','ドメイン','サーバー','レンタルサーバー'],
                'issued' => '2025-12', 'status' => 'active'],
  'fp_cafe' => [..., 'issued' => '2026-07', 'status' => 'active', 'default' => true],
];
```

- テンプレート側は `zidooka_render_ad('post_title_top')` を呼ぶだけにする
- **すべての広告**（AdSense/A8問わず）が共通レンダラを通る
  → ラベル表示・PostHog計測・lazy loadingが自動で統一される
- 案件の追加・停止は `zidooka_a8_offers()` の編集だけで済む

### 3.3 計測の統一

**イベント設計（PostHog）** — provider横断で同じイベント名に統一:

```
ad_impression { provider: 'adsense'|'a8', placement: 'post_title_top'|..., offer? }
ad_click      { provider, placement, offer? }
```

現状の `ad_click`（AdSense用）と `banner_click`/`banner_exposure`（A8用）が
バラバラなので、共通レンダラ導入時に上記へ寄せる。

**A8成果の取り込み** — A8に公開APIはないので、
月1回A8管理画面から成果CSVをダウンロードして `data/ads/a8/YYYY-MM.csv` に置く運用にする。
`npm run improve`（自己改善ループ）がこのディレクトリを読むようにすれば、
AdSenseと同じテーブルに乗る。

**共通KPI**: プレースメントごとに「収益 ÷ 表示1000回（RPM相当）」で
AdSenseとA8を同じ物差しで比較する。A8は `発生報酬 × 承認率見込み` で換算。

## 4. 組み直し本体に向けた論点（次のステップ）

管理基盤（上記3）を入れた後、配置の組み直しで検証したい仮説を優先度順に:

1. **タイトル直上広告(A2)の是非** — ファーストビューを広告が占有しCLS/LCPにも不利。
   「タイトル直上を外して本文内（最初のh2直後）へ移す」が最有力候補。
   B1と同じ `the_content` フィルタ方式で実装できるが、`</p>` split は壊れやすいので
   DOMベースか正規表現でh2を探す方式にする。
2. **本文内AdSense（真のin-content）** — 現状A3は実質「本文下」。
   長文記事では本文中間に1枠追加する価値がある。エラー解決系の読者は
   答えを見つけたら離脱するので、本文前半〜中盤の価値が高いはず。
3. **サイドバーのデフォルト案件** — FPカフェは読者属性とズレ。
   技術系読者に合うA8案件（レンタルサーバー、VPS、プログラミングスクール、
   AIツール系）へ差し替え候補を探す。もしくはデフォルトはAdSense
   （レスポンシブ）にしてA8はタグ一致時のみ、という構成も比較したい。
4. **カレンダーページの収益化** — トラフィックの15%を占めるのに広告との相関が
   弱いと分析済み（`drat/20260527-adsense-integrated-analysis.md`）。
   専用プレースメントを台帳に追加して個別に計測する。
5. **Auto ads / アンカー広告 / vignette の方針** — 現状は手動ユニットのみ。
   有効化するなら「セッションあたり広告3枠まで」の既存ポリシーと矛盾しないか
   先に決める。

**検証の進め方**: 既存ルール通り PostHog A/Bは同時1本（`zdk_*` フラグ、
サーバーサイド割当）。1変更 = 1 `docs/decisions/` 記録。
P2（スロット分離）が済んでいないと効果測定できないので、順序は必ず
「スロット分離 → 管理基盤 → 配置A/B」。

## 4. 広告A/Bテスト基盤（2026-07-09 導入）

サイドバー広告のデフォルト案件について、複数のオファーを重み付きランダム割当でテストできる仕組みを `inc/ads.php` に追加した。

### 仕組み
- プレースメント設定に `ab_test` キーを追加すると、タグ不一致時のフォールバック選択が重み付きランダムになる
- `variants`: テスト対象のoffer IDリスト
- `weights`: 各variantの選択確率（整数。合計が100になる必要はない）
- `ad_impression` / `ad_click` PostHogイベントに `ab_experiment` / `ab_variant` プロパティが自動付与される
- タグ一致案件は常に最優先（A/Bテストの対象外）

### 現在の実験
| 開始日 | プレースメント | バリアント | 重み | 判定予定 |
|--------|--------------|-----------|------|---------|
| 2026-07-09 | sidebar | fp_cafe (control) / techgo_banner | 50/50 | 2026-07-23 |

### 使い方
- 実験終了後: 勝ちバリアントを `default: true` に変更し、`ab_test` を削除する
- 新規実験: 別のプレースメントにも同様に `ab_test` 設定を追加可能
- 管理画面JSONでも上書き可能（例: weights変更、variants追加）

## 6. 突発キャンペーン運用（2026-07-10 導入）

`inc/ads.php` の `campaigns` 台帳で、キャンペーンごとに `start` / `end` / `status` / `click` / `img` を管理する。有効期間中は `campaigns` を指定したプレースメントで通常案件より優先配信される。現在は `campaign_top` と `sidebar` が対応している。

キャンペーンの表示・クリックは通常広告と同じ `ad_impression` / `ad_click` に `provider: campaign` と `campaign` を付けて計測する。終了後は期間判定で自動停止し、管理画面の Ads Settings で一覧を確認できる。次回のセールはキャンペーンを追加し、対象プレースメントの `campaigns` 配列へIDを指定する。

## 7. サイト間導線

フッターから `www.zidooka.com`、`tools.zidooka.com`、`tools.zidooka.com/jp/calendar` へ通常リンクを設置している。これはZidooka本体の直接的な検索順位を保証するものではないが、サイト間の発見性・回遊・ブランド導線として有効で、`nofollow` は付けない。
